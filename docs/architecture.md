# Архитектура

## Общая схема

```text
путь
  │
  ▼
openat / getattrlistbulk ──► TreeBuilder ──► ScanTree ──► SwiftUI
  │                            (арена)        │
  │                                           ├─ карта (treemap)
  └─ readdir + fstatat (fallback)              ├─ таблицы
                                               ├─ типы
                                               └─ крупнейшие / очистка
```

## Сканер

Сканирование начинается с проверки, поддерживает ли файловая система
`getattrlistbulk`. Для каждого каталога:

1. `openat(parentFD, name, O_DIRECTORY)` — дескриптор не хранится для всех
   каталогов сразу, поэтому глубина рекурсии ограничена только глубиной пути.
2. `getattrlistbulk` с буфером 256 КБ запрашивает:
   `ATTR_CMN_RETURNED_ATTRS`, `ATTR_CMN_NAME`, `ATTR_CMN_OBJTYPE`,
   `ATTR_DIR_MOUNTSTATUS`, `ATTR_DIR_ALLOCSIZE`, `ATTR_FILE_ALLOCSIZE`.
3. Точки монтирования (`DIR_MNTSTATUS_MNTPOINT`/`TRIGGER`) пропускаются:
   приложение не уходит на другие тома и не считает один и тот же APFS-контейнер
   дважды.
4. Симлинки не разыменовываются и получают нулевой размер.
5. Каталоги с расширениями `.app`, `.photoslibrary`, `.fcpbundle` и подобными
   помечаются как пакеты: они сканируются внутри для точного размера, но в
   рейтингах и очистке участвуют как один объект.

Для файловых систем без `getattrlistbulk` есть запасной путь:
`readdir + fstatat(AT_SYMLINK_NOFOLLOW)`. Он медленнее, но сохраняет ту же
модель дерева.

Прогресс отправляется не чаще 10 раз в секунду; отмена проверяется между
пачками записей и каталогами. Ошибки доступа не прерывают скан: путь
запоминается в выборке, а счётчик пропущенных объектов показывается в баннере.

## Дерево

`ScanNode` — компактная структура: смещение и длина имени в общем
UTF-8-блобе, родитель, диапазон детей, количество файлов, размер, тип и
доминирующая категория. Имена не дублируются строками, поэтому миллионы узлов
занимают десятки мегабайт.

- Файлы меньше 64 КБ агрегируются в узел `aggregate` внутри своей папки:
  «Мелкие файлы». Суммы остаются точными, а память не растёт линейно от
  количества мелочи.
- После обхода один обратный проход суммирует размеры и количество файлов от
  листьев к корню. Второй проход вычисляет доминирующую категорию контейнера
  по самому крупному ребёнку — она используется для цвета на карте.
- Удаление не мутирует существующее дерево. `removingSubtrees(at:)` создаёт
  копию (copy-on-write) и вырезает поддеревья, поэтому фоновый расчёт
  статистики не гоняется с изменениями. GUI сразу получает новое дерево.

## Карта

Раскладка — squarified treemap (Bruls, Huizing, van Wijk). Строятся два уровня:

1. Дети текущей папки, отсортированные по размеру; крупнейшие 320 — отдельные
   ячейки, остальные — «Ещё N».
2. Для контейнеров площадью больше порога дети раскладываются внутри с
   отступом и полосой 18 pt сверху. На полосе — имя родителя и размер.
   Вложенность ограничена 32 детьми и общим бюджетом в 700 подячеек.

Цвет ячейки берётся из категории (видео, изображения, аудио, архивы,
документы, приложения, код, другое). Для контейнеров без выраженной категории
используется вращающаяся холодная палитра, чтобы карта из одних `.app` не
превращалась в однотонное пятно. Для светлых категорий текст автоматически
становится тёмным.

## Потоки и состояние

- Скан выполняется на отдельной последовательной очереди; UI получает
  прогресс через `DispatchQueue.main`.
- `ScanTree` неизменяем после скана (кроме copy-on-write удаления), поэтому
  фоновые вычисления «Крупнейших» и «Типов» читают его без блокировок.
- Результаты фоновых вычислений применяются только если дерево всё ещё то же
  самое (проверка идентичности и поколения).
- Таблица текущей папки показывает не больше 2500 самых крупных детей; для
  больших каталогов это защищает интерфейс от десятков тысяч строк.

## Точность

Сумма скана сравнивается с `du -sk` в тестах; на реальных каталогах
(`/Applications`, Xcode) значения совпадают. Отличия возможны из-за:

- жёстких ссылок — они считаются по каждому пути, а `du` дедуплицирует;
- клонов APFS — учитываются как обычные файлы;
- снимков APFS и purgeable-пространства — они не входят в дерево.

Подробнее — в разделе [Ограничения](limitations.md).

## Производительность

- `/Applications` (53,1 ГБ, 698 004 файла): несколько секунд на тёплом кэше.
- Домашняя папка (238 ГБ, 3,1 млн файлов): около 4 минут на холодном кэше,
  с прогрессом и возможностью отмены.
- Память: около 1,06 млн узлов для домашней папки; плоские массивы и
  агрегация мелких файлов держат footprint в десятках-сотнях мегабайт.
